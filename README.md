# Brain-Spine Orchestrator (BSO)

> **Дослідницький симулятор / цифровий двійник** оркестраційного шару для
> стимуляційної сторони brain-spine інтерфейсу (BSI).
> **Це НЕ медичний пристрій і НЕ прошивка реального стимулятора.** Жодного коду до
> реального заліза, імплантів, телеметрії чи пацієнтських даних. Усі числові межі —
> **ілюстративні плейсхолдери**, не клінічно валідовані.

Автор концепту: Ігор Шаранда (1ТМО / Unbroken). Повний канон — у [`CLAUDE.md`](CLAUDE.md).

## Що це

Програмний шар, що сидить **між декодером наміру (мозок) і спинальним
стимулятором (EES)**. Він перекладає високорівневий намір руху («стояти», «йти»,
«сходи») у скоординовані просторово-часові патерни стимуляції десятків м'язових
груп, адаптує їх за сенсорним зворотним зв'язком і **гарантовано тримається в
межах безпеки**. Мозок не замінюється — намір волевий, шар лише перекладає й
оркеструє його нижче рівня ушкодження.

Хода моделюється **фазово (CPG-подібно)**, як у реальних BSI (leading clinical research centers,
платформа a partner platform ARC), а не як наївний мапінг «м'яз → напруга».

## Швидкий старт

```bash
cd brain-spine-orchestrator
python3 -m pip install -e ".[viz,dev]"   # або: pip install numpy scipy matplotlib pytest

# критичні safety-тести + повний набір
python3 -m pytest -q

# демо-сценарії (рахують метрики + рендерять PNG/GIF у outputs/)
python3 scenarios/walk.py          # хода + збурення балансу -> відновлення
python3 scenarios/sit_to_stand.py  # сидячи -> стоячи
python3 scenarios/stairs.py        # WALK -> STAIRS_UP -> WALK
python3 scenarios/resilience.py    # втома+дрейф: адаптація проти волочіння стопи
python3 scenarios/walk_mujoco.py   # та сама хода на ДИНАМІЧНІЙ фізиці MuJoCo
python3 scenarios/stress_physics.py  # стрес: втома + шум сенсорів на фізиці
python3 scenarios/learn_adaptation.py  # навчена політика Шару 4 (CEM) vs інтеграл
python3 scenarios/coupling_study.py    # де навчання виграє (channel coupling) — і де ні
python3 scenarios/balance_recovery.py  # активне відновлення рівноваги після поштовху
python3 scenarios/autonomic_demo.py    # сечовий міхур / кишківник / еректильна функція
python3 scenarios/managed_bladder.py   # замкнутий контур міхура: авто-спорожнення, без АД
python3 scenarios/muscle_gait.py       # Hill-модель м'язів (динаміка активації + FL/FV)

# Інтерактивний веб-дашборд (нуль залежностей, для живих демо партнерам):
python3 web/server.py                  # відкрий http://localhost:8765
```

Результати: `outputs/*_summary.png` (намір→фази→активації→стим→сенсори) і
`outputs/*.gif` (фігурка-паличка у сагітальній площині).

## Автономні функції — нарівні з ходьбою

Для людей зі спінальною травмою відновлення **сечового міхура, кишківника й
еректильної функції** цінується нарівні або вище за ходьбу. Той самий
EES-субстрат націлюється на попереково-крижові автономні контури (S2–S4).
`bso/autonomic.py` моделює:

- **Сечовий міхур** — детрузор-сфінктерна дисинергія (DSD) проти координованої
  нейромодуляції. Контраст у демо: DSD → тиск 94 cmH₂O, залишок 184 мл,
  **автономна дисрефлексія** (АТ +51 мм рт.ст., загроза життю); координація →
  54 cmH₂O, повне спорожнення, **0 подій АД**.
- **Кишківник** — пропульсія + розслаблення сфінктера (повніше спорожнення).
- **Еректильна** — парасимпатична (S2–S4) тумесценція.
- **AD-монітор** — проксі систолічного АТ від розтягнення; центральна life-safety.

Це той самий принцип, що й хода: відновити СИНЕРГІЮ контурів, а не керувати
кожним мʼязом окремо. Демо: `scenarios/autonomic_demo.py`.

## Архітектура (6 шарів + супервізор)

```
 Шар 0 Decoder  →  Шар 1 Orchestrator  →  Шар 2 Effectors  →  StimCommand
 (намір)            (CPG / фази ходи)      (м'язові групи)          │
    ▲                    ▲                      ▲          Шар 5 SAFETY (вето)
    │                    │                      │                   │
    │               Шар 3 Feedback  ◄────────  SensorFrame ◄── BioMech model
    │                    │
    │               Шар 4 Adaptation (повільно, між сесіями)
    └──── Супервізорний LLM (конфіг, звіти — НЕ в realtime)
```

| Шар | Файл | Роль | Тип |
|---|---|---|---|
| 0 | `decoder_stub.py` | джерело наміру (сценарій) | заглушка |
| 1 | `orchestrator.py` | CPG + фазовий годинник → `MuscleTarget` | детермінований контролер |
| 2 | `effectors.py` | activation → `StimCommand` (інверсна крива рекрутингу) | детермінований мапер |
| 3 | `feedback.py` | sensor fusion → `GaitState` + корекції | оцінювач стану + детектори |
| 4 | `adaptation.py` | дрейф/втома/симетрія між сесіями | офлайн-оптимізація |
| 5 | `safety.py` | **вето над кожною командою**, clamp/block/e-stop | детермінований, без ML |
| — | `runtime.py` | складання замкнутого контуру | інфраструктура |
| — | `supervisor_llm.py` | звіти/конфіг протоколу поза realtime | LLM (опц.) + фолбек |

## Safety-інваріанти (ніколи не порушуються)

1. Тільки симуляція — жодного реального заліза.
2. Мозок не замінюється — декодер лише читає намір.
3. `safety.py` має **абсолютне право вето** над кожною `StimCommand`.
4. Хард-ліміти — константи в `config/limits.py`, ніколи не перевищуються.
5. LLM **ніколи** не в реальному моторному циклі.
6. Жодних реальних пацієнтських даних.

`tests/test_safety.py` покриває це вичерпно і не може бути послаблений.

## Стан реалізації (дорожня карта канону)

M0 каркас · M1 safety+тести · M2 біомех+стимулятор · M3 CPG-диригент ·
M4 ефектори+замкнутий контур · M5 сценарії+візуалізація · M6 адаптація+LLM-звіт
— **усі виконані** (див. `CLAUDE.md §7`).

**M7 (понад канон) — адаптивна стійкість, наш диференціатор:** модель деградації
плану (`degradation.py`: втома + дрейф) + **онлайн-адаптація Шару 4**
(`OnlineAdaptation`, повільний інтегральний контролер між циклами, не в ms-петлі).
Демо `resilience.py` показує три умови: норма / деградація без адаптації
(волочіння стопи) / деградація + адаптація (кліренс утримано в межах safety).
Чесний trade-off видно: компенсація прискорює накопичення втоми.

**M8 (понад канон) — динамічна фізика:** бекенд **MuJoCo** (`biomech/mujoco_model.py`)
— планарний двоногий із підвісом розвантаження ваги; той самий CPG+safety, але PD-
трекінг дає МОМЕНТИ, а MuJoCo рахує динаміку й реальні контактні сили (без RL-падінь).
`walk_mujoco.py`: хода тримається вертикально (таз 0.90 м, тулуб <6°), GRF ≈ вага
тіла з чергуванням опори −0.96, 0 порушень safety. Підставляється через
`build_system(model=MuJoCoModel())` — решта шарів без змін.

**M9 (понад канон) — стрес-батарея на фізиці (M7 × M8):** модель псування сенсорів
(`sensors.py`: гаусів шум + дропаут кадрів) + `stress_physics.py` — чотири умови на
MuJoCo-тілі. Результат: під втомою кліренс стопи падає до ~77%; з онлайн-адаптацією
Шару 4 — ~98%; **навіть із шумними/підвисаючими сенсорами — ~100%**, таз тримається
~0.90 м, баланс 100%. Адаптація робастна до шуму зворотного зв'язку.

**M10 (понад канон) — навчаний Шар 4 + ЧЕСНИЙ негативний результат:**
`learned_adaptation.py` — мала нейрополітика (numpy MLP), навчена офлайн методом
cross-entropy (CEM) проти симулятора; save/load, оцінка на відкладеній умові +
перенос на MuJoCo. **Висновок (чесно): рукотворний інтегральний контролер —
near-optimal baseline для цієї одно-цільової задачі, і навчена політика його НЕ
перемагає (і гірше переноситься на фізику).** Це корисний негативний результат:
тут складність навчання не виправдана. Цінність навчання — гіпотеза для багатших
постановок (координація десятків каналів, часткова спостережуваність, клінічні
мульти-цілі), які цей trainable-харніс тепер дозволяє досліджувати.

Наступний крок — багатовимірна постановка для навчання; м'язово-скелетна модель
OpenSim; веб-дашборд; активний trunk-баланс на MuJoCo.
